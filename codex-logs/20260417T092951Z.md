Topic: Analyze current FM2 velocity-field implementation and assess replacing the first FMM distance field with ESDF for better performance in dynamic environments.
Decisions
- Confirmed the current FM2 velocity field computes obstacle distance with a first FMM pass in `fastmarching2.hpp`, then maps distance to velocity and runs a second FMM over the velocity field for arrival times.
- Confirmed the first-pass result is cached as `base_velocity_map_`; it is not recomputed every plan unless occupancy is refreshed and `invalidateVelocityCache()` is triggered.
- Identified that current dynamic obstacles are handled by uncertainty injection on the cached velocity map rather than by rebuilding the obstacle-distance field each cycle.
- Concluded that an ESDF replacement would give the clearest benefit only when the underlying occupancy map changes often enough to invalidate the cache, or if the system is redesigned to maintain a live incremental distance field.
- Identified three relevant external algorithm families:
- static/full recompute exact EDT via Felzenszwalb-Huttenlocher
- incremental occupancy-based ESDF via FIESTA
- incremental octree/voxel EDT/ESDF via dynamicEDT3D, Voxblox, and nvblox
